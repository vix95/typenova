# TypeNova architecture

The single technical reference of the repository. It describes how the application is built and the rules that keep it correct. What changed in each release is in [CHANGELOG.md](CHANGELOG.md); user-facing features are in the [README](../README.md).

TypeNova is a local-first desktop Markdown workspace: TypeScript + Vite in a Tauri 2 / Rust shell, CodeMirror 6 for editing, a Web Worker for Markdown. Documents on disk are authoritative; nothing is sent to a network service.

## 1. Source layout

| Path | Responsibility |
|---|---|
| `src/main.ts` | Thin composition root. Imports the feature modules and runs the boot sequence. No feature logic. |
| `src/app` | Shell: `$` helper, workspace scaffolding, sidebar, command palette, menu/toolbar/settings/global bindings. |
| `src/ui` | Reusable UI infrastructure: tooltip, themed select, dialogs, toast, `icons.ts` (SVG icon set). |
| `src/i18n` | Polish/English switching: phrase table, `applyLanguage`, `langText`. |
| `src/editor` | CodeMirror: extensions, completions, snippets, minimap, scroll sync, Math and Mermaid editors, format document. |
| `src/documents` | Open documents: state, tabs, dirty flag, file actions, recovery, session restore. |
| `src/preview` | Preview pipeline: worker client, virtual window, fallback, code blocks, Mermaid, export/print, media/PDF/TIFF viewers, structured (JSON/XML) tree, page preview. |
| `src/outline`, `src/layout` | Heading outline and breadcrumbs; pane widths, appearance, focus mode, splitters. |
| `src/project`, `src/filesystem` | Project explorer UI; pure filesystem logic (paths, file kinds, encodings, tree operations). |
| `src/graph`, `src/graph-ui` | Section graph: renderer-independent model and workers (`graph`); state, indexing, Tree / Flat canvas / Globe renderers and interactions (`graph-ui`). |
| `src/git-ui` | Read-only Git history dialog (graph, commit list, detail, diff). |
| `src/preview.worker.ts` | Markdown parsing and rendering worker. |
| `src/style.css`, `src/styles/` | `style.css` only imports `foundation.css`, `theme-project.css`, `graph-workspace.css` in that order; the order is the cascade. |
| `src-tauri/` | Rust host: commands, capabilities, filesystem scope, `page_server`, `git`, `clipboard_files`. |
| `tests/`, `benchmarks/`, `examples/file-types/` | Node tests, graph indexing benchmark, reproducible sample files per supported type. |

Element ids and `localStorage` keys still use the former `brain` prefix (`#brainView`, `typenova.brain.*`); they are persisted or shared with CSS and were deliberately kept.

## 2. Module contract

- A module's top level contains **declarations only**. Anything with a side effect (event listeners, DOM setup) is in an exported `init*` function that `main.ts` calls once, at the position where the behaviour must run. Registration order is behaviour: several handlers share `document` `keydown`, and the language pass snapshots the DOM text nodes that exist at that moment.
- State written from more than one module lives in a small exported state object owned by one module: `documentState`, `previewState`, `outlineState`, `scrollSyncState`, `minimapState`, `layoutState`, `graphUi`. Do not export a mutable `let`.
- `tests/module-structure.test.mjs` enforces: functions ≤ 100 lines, modules ≤ 600 lines, every `init*` called exactly once from `main.ts`, worker `new URL(…, import.meta.url)` paths resolve.
- Pure modules (no DOM, no Tauri) are compiled and tested by `npm test`. A new pure module imported by a test must be added to the file list of the `test` script, with `.js` suffixes in its relative imports.
- `tsconfig.json` enables `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`, `noFallthroughCasesInSwitch`; `$` is generic (`$<HTMLInputElement>("id")`).

## 3. Editing and preview performance

The per-keystroke path never calls `doc.toString()`, tokenizes Markdown, counts words or compares whole documents.

1. **UI thread**: CodeMirror transactions, selection, layout, virtual preview window, dirty flag, scroll coordination.
2. **Markdown worker**: parses the current snapshot, builds source-mapped top-level block metadata, the outline and statistics, keeps parser tokens for the current revision, renders only requested block indexes. Export/print uses a separate worker so virtualization stays on during editing.
3. **Virtual preview**: mounts a visible range plus overscan; estimated heights keep a scrollable document, measured heights refine them; off-screen DOM is evicted and re-rendered from retained tokens without reparsing. Blocks removed from the window must not cache a height of 0 px (it makes the preview jump).
4. **Heavy blocks**: a very large block shows a placeholder; rendering it is explicit, with a confirmation above 1 MB. Mermaid renders only near the viewport.

Correctness rules:
- Stable source-block keys; parser-mode and reference-definition changes invalidate caches; heading keys include a context signature because anchor ids depend on other headings.
- Every worker request carries the document revision; stale results are discarded, one request is in flight, pending work is coalesced to the latest snapshot.
- Parsing stays a full-document pass (reference links, nested lists, fences and heading ids cross block boundaries); it is off the UI thread and only visible blocks render.
- Documents ≥ 2 million UTF-16 code units use a performance profile (no bare-URL autolinking or typography, no highlighting of code blocks > 8 KB). Above 1 MB the editor drops active-line highlighting only; fold gutter stays. Syntax modes other than Markdown are off from 750,000 code units.
- Do not advertise performance figures that were not measured on a real release build.

## 4. Section graph

`src/graph` holds a renderer-independent section model (`buildSectionNodes`: scan headings, fill section content, resolve wikilinks), spatial queries and the workspace controller; indexing runs in a worker with progress and cancellation. The UI offers three renderers over the same model: Tree (dedicated layout), Flat (one Canvas 2D surface) and Globe (SVG projection).

- No node or edge cap, sampling or truncation: the whole filtered model stays in memory; only drawing is limited to what is visible.
- **Flat canvas**: adaptive pixel ratio; pan/zoom transforms the last frame with CSS and repaints once the interaction settles; spatial hash for hit-testing and viewport queries (rebuilt only when positions change); segment grid for edges with an overflow list for very long edges; edge redraw deferred during drags; layout and drawing batched over animation frames with reused typed arrays.
- **Level of detail** (`src/graph/lod-policy.ts`, shared by Flat and Globe): from 200 visible vertices only a fraction (20% overview ratio) is drawn, growing with zoom to full detail at a threshold scaled by √(vertex count). Vertices are ordered by heading level first (H1 before H2, …), then by degree, then by a stable key, so the same vertices appear for the same zoom. Labels are independent from collision suppression: disabled labels stay hidden even on hover.
- Ambient motion is off by default and throttled (2D redraws at most every 50 ms; Globe has its own frame interval).
- Graph and Tree are two modes of one workspace: whole-module controls behave consistently in both; the Graph/Tree switch keeps exactly one option selected and synchronizes `.is-active` with `aria-pressed`. `body.graph-mode` hides the top-bar Save and Preview buttons (Save remains in the File menu and Ctrl+S).
- Considered and not adopted: Sigma.js/Graphology (WebGL, strongest candidate if Canvas becomes insufficient, needs a full compatibility pass), Cytoscape.js, d3-force, Three.js instancing, a force-layout worker. Benchmark on a representative workspace before any migration. `npm run benchmark:graph` measures indexing; `benchmarks/baseline-*.json` are reference results.
- **Following links** (`src/preview/wiki-link-plugin.ts`, `src/editor/wiki-link-extension.ts`, `src/app/wiki-link-navigation.ts`): the preview renders `[[links]]` as anchors (markdown-it rule, shared by the worker and the main-thread renderer); a click, or Ctrl+click in the editor, resolves the target with `resolveLinkTarget` (the planner's resolver, i.e. the graph's rules) over the open documents, the one file a link names (`[[file.md#Header]]`), and the link index. Typing `[[` completes the file and then its sections (`src/editor/link-completion.ts`). **Link index** (`src/graph/project-index-model.ts` pure, `src/filesystem/project-index-store.ts` scan and storage, `src/documents/project-index.ts` state): for every Markdown file its sections and what its links name, found with a stat per file (only changed files are read), stored in the app data folder (`link-index/<key>.json`, needs `fs:allow-stat`), warmed when a Markdown tab is shown, renewed on save (`noteFileSaved`) and rechecked when older than 30 s. A rename reads only the files whose links name the old title and plans over their texts plus the outlines of all others (`sourcesFromIndex`); `planQualifyLinks` writes bare `[[Title]]` links in full (command palette).
- **Heading rename** (`src/editor/heading-rename.ts`, `src/documents/link-rename-apply.ts`, pure planner `src/graph/link-rename.ts`): the editor tracks an edited heading and, once the edit settles (caret leaves the line, blur, save, tab switch or 5 s idle), the planner finds the `[[links]]` that resolve to it with the same rules as the graph. Open tabs are edited as annotated transactions (ignored by the tracker); other project files are rewritten on disk only if unchanged since they were read, keeping their line endings. Ambiguous links (shared titles in other files), titles holding `[ ] | #`, case-only renames and projects over 3000 files are left alone and reported. Setting `typenova.autoRenameLinks`, default on.

## 5. Files, encodings and viewers

- **File kinds** (`file-types.ts`): markdown (`.md`, `.markdown`, `.mdown`, `.mkd`, `.mdx`, `.rmd`, `.qmd`, `.mdc`), about 340 text extensions plus names such as `Dockerfile`, `Makefile`, dotfiles; unknown extensions are tried as text and binary content (NUL, control characters) is refused. Images, PDF, audio, video, TIFF and Word have their own handling.
- **Encodings** (`text-codec.ts`, `text-io.ts`): files are read as bytes and decoded in their own encoding (UTF-8 with/without BOM, UTF-16 LE/BE, Windows-1250/1251/1252, ISO-8859-2/15); invalid UTF-8 is guessed as Windows-1250 or ISO-8859-2. They are written back in the same encoding and line endings (CRLF/LF/CR; the editor works on LF). The status bar shows both and can reopen a file in another encoding.
- **Previews**: CSV/TSV as a table (2000 rows), `.mmd`/`.mermaid` as a diagram, JSON (`json`, `geojson`, `jsonld`) and XML family (`xml`, `xaml`, `axaml`, `xsd`, `xsl`, `rss`, `atom`, `opml`, `csproj`, `resx`, `plist`, …) as a lazily expanded tree with expand/collapse all (limits: 5000 items, depth 24, text 300 characters; an error keeps the last valid tree), `.canvas` as a Mermaid flowchart, PDF (pdf.js), TIFF (UTIF), audio/video in a TypeNova player with seek, volume, speed and shortcuts. `![](clip.mp4)`, audio and PDF embed in Markdown.
- **Data view and charts** (`src/data/`): CSV, TSV, `.tab` and TXT files open read only in a dialog with Table, Profile and Charts tabs; from 50 MB (`LARGE_FILE_BYTES`) they open there instead of the editor (the dialog offers "Editor", with a warning above 300 MB), and the tree's context menu, the command palette and the File > Open path reach it for every size. The file is never in memory as a whole: the window reads it in 4 MiB pieces with the fs plugin (`fs:allow-open` and `fs:allow-read`, the same path scope as before), transfers them to `data.worker.ts`, and at most two pieces are in flight. The worker decodes (BOM, UTF-8, else Windows-1250 / ISO-8859-2, UTF-16), detects the delimiter (`,` `;` tab `|`, or none for plain text) from the first 64 KB and runs the pure modules: `delimited-stream.ts` (RFC 4180 parser that keeps its state between pieces), `column-stats.ts` / `data-profile.ts` (one pass: counters, Welford mean and deviation, a 20,000-value reservoir sample for median, quartiles and histogram, a table of at most 5,000 distinct values that is dropped when exceeded), `chart-job.ts` (grouped aggregates capped at 50,000 keys, a sample for histograms and scatter plots), `chart-svg.ts` (SVG text, colours are CSS variables, every label escaped). Medians, quartiles, histograms and scatter plots are therefore approximate above the sample size and the viewer says so; counts, sums, minima, maxima and means are exact. A result is cached per file version (size and modification time), 12 entries.
- **Preview pane of CSV, TSV and TXT** (`data-preview.ts`, same pattern as the JSON/XML tree: a section after `#preview`, `.preview-pane.data-mode` hides the Markdown view): tabs Data (the first 500 rows) and Charts (tiles, then one chart for every column by the type found in its values, chosen by `overview.ts` from the first 256 KB: a histogram for numbers, the rows over time for dates, the rows per value for categories and yes/no; the figures of the column under it; a card only for columns that cannot be charted, such as free text; nothing depends on column names). The text of the open document is analysed by the same worker with the `overview` job (profile and the chart jobs in one pass; `runDataJobOnText`), 400 ms after the last edit and only while the preview is visible; the tabs are the application's own `.preview-view-tab`. A TXT without a delimiter is one column of lines without a header row.
- **Chart wizard** (Charts tab of the data view, `data-view-charts.ts`, steps in `data-wizard-steps.ts`, rules in the pure `chart-wizard-model.ts`): step 1 chooses a goal (compare groups, change over time, spread of values, relation of two numbers; each says whether the file fits), step 2 completes a sentence ("Show the total of amount for each country"), step 3 sets a title and inserts the block into a note chosen from the saved Markdown notes open in tabs (at its cursor, the block is then selected) or copies it; the chart is drawn live from the whole file. Measures are the number columns in the order of the file, a column of running numbers or constant values last; names of columns are never interpreted. The command palette entry "Insert a chart from a data file into the note…" chooses a file and opens the wizard on the Charts tab.
- **Chart blocks in notes**: a fenced ```chart block (`file`, `type` bar/line/histogram/scatter, `x`, `y`, `agg`, `top`, `bins`, `by`, `title`; see `chart-spec.ts`) is passed by the preview worker as `<pre><code class="language-chart">` and drawn by `chart-embed.ts` (`observeCharts`, called next to `observeMermaid`). The file is named relative to the note and must stay inside the note's project folder (beside the note when there is no project); charts are computed one at a time, and the last drawing of a block is shown at once when the virtual preview mounts it again. "Insert into note" in the viewer writes the block with a path relative to the saved Markdown note. Nothing in a block is executed, and a block cannot name a drive or a URL.
- **HTML pages** (`page-preview.ts`, `src-tauri/src/page_server.rs`): the saved page is shown in an `<iframe sandbox="">` (no scripts) loaded from the custom `tnpage` scheme, so relative CSS, images and fonts resolve inside the project folder. Scripts run only after the user enables them (`allow-scripts`, never `allow-same-origin`). The scheme serves only web file types, only inside the registered root, with a per-response CSP that forbids network access and frames. On Windows `canonicalize` yields a `\\?\` prefix that must be stripped before `starts_with` comparisons.
- **Format document** (Shift+Alt+F): JSON, JSON Lines, YAML (comments kept), XML, Markdown tables; TOML is validated.
- **Import**: Word `.docx` (mammoth) and HTML (turndown) become Markdown in a new tab. PDF, TIFF and Word code is loaded lazily.
- **Not supported**: HEIC/JPEG XL, RTF/ODT/Excel import, editable CSV grid, PlantUML/Graphviz drawing, reformatting JSONC/JSON5/HTML/CSS/JS.
- **Sample files**: `examples/file-types/samples.mjs` is the single source for sample files and `manifest.json`; `generate-samples.mjs` writes them (`--check` compares). They are stored byte-exact (`.gitattributes` `-text`), including CRLF and `server.log`.

## 6. Project tree and file operations

- The open folders of the tree are remembered in `typenova.project.expandedFolders` (`src/project/expanded-folders.ts`, list rules in the pure `src/filesystem/expanded-folders-model.ts`): restored once per set of project folders when the tree is drawn, saved after every toggle and every draw; other projects' entries are kept.
- Several project folders can be open at once; the tree refreshes when files change on disk (F5 for manual refresh) and accepts files dragged from the system file manager.
- Internal clipboard (Ctrl+C/X/V, context menu) stores a path and copy/move mode; files and folders copied in the system file manager are pasted via a Rust command (`clipboard_file_list`, `paste_clipboard_files`) with collision-safe names.
- Drag and drop moves into folders or the project root; moves into the source or its descendants are rejected, existing files are never overwritten (copy-suffixed names), folder copy is recursive and an incomplete destination is removed, a failed native rename falls back to copy-then-remove, and open-tab paths are updated.
- Images open from the tree with a hover thumbnail; paste of a clipboard image asks for a description, file name and folder inside the project.

## 7. Filesystem security

- Access is tied to what the user selected. The folder dialog requests recursive scope; `tauri-plugin-persisted-scope` restores grants after restart; a project path without a grant offers "Choose folder" instead of a misleading retry. Never grant whole drives and never widen `src-tauri/capabilities/default.json` for convenience (it enables only the fs commands the app needs, including `exists`, `rename`, `remove`).
- **Asset protocol** scope is `$HOME/**` and `$APPDATA/**`; `tests/tauri-config.test.mjs` fails if it is widened. Local images outside it are granted one file at a time by `allow_preview_image` (canonical path, existing regular file, image extension only, read-only, not persisted). Audio, video and PDF use the same per-file grant. A placeholder with a localized label is shown when an image cannot be loaded. Trade-off: a Markdown file the user opens can make the preview display any existing image file it names; the CSP still forbids network exfiltration.
- **CSP** (`tauri.conf.json`): `connect-src` is limited to IPC; `frame-src` allows only the `tnpage` scheme. Tauri adds a nonce to `style-src` in production builds, which makes browsers ignore `'unsafe-inline'` and blocks every inline style (CodeMirror stylesheets, KaTeX, tooltips); `dangerousDisableAssetCspModification: ["style-src"]` prevents this and a test guards it. This only shows in production windows, never in the dev server or a plain browser.
- **Browser features are off** (`harden_webview`, Windows/WebView2): devtools, browser accelerator keys, zoom, status bar, autofill. `initBrowserShortcutGuard` also blocks F12, F5, Ctrl+Shift+I/J/C/R, Ctrl+U/R/H/J, zoom keys and Ctrl+wheel on all platforms. Ctrl+P is swallowed and does not print; printing stays in the File menu.
- File content is data, never executed. User-content output is escaped or sanitized through the existing rendering conventions; Git commands run in Rust with validated arguments and read-only.

### Integrated terminal (processes, project config and trust)

- **Rust** (`src-tauri/src/terminal.rs`): `terminal_shells` lists the shells of the computer (PowerShell 7, Windows PowerShell, cmd, Git Bash, WSL and others found in PATH on Windows; /etc/shells and $SHELL elsewhere), `terminal_spawn` starts one in a pseudo terminal (`portable-pty`: ConPTY on Windows) in a folder that exists, `terminal_write`, `terminal_resize` and `terminal_kill` drive it, and all shells are ended when the last editor window closes. Output is streamed through a `Channel` as base64 (a byte stream: a character may be split between chunks). On Windows ConPTY only ends its output when it is closed and asks the terminal where the cursor is (ESC [ 6 n) before it goes on: a separate thread waits for the child, lets the last output drain, emits the exit and drops the session (its generation number stops a late exit of an old session from removing a newer one with the same id), and xterm.js answers the cursor request. `cargo test` runs real shells through the pseudo terminal (output, input, resize, exit code).
- **Frontend** (`src/terminal/`): `terminal-model.ts` is pure and tested (config parsing, names, folders, trust hashes, custom shells); `terminal-backend.ts` wraps the commands; `terminal-session.ts` joins an xterm.js screen (`@xterm/xterm`, `@xterm/addon-fit`) to a shell; `terminal-theme.ts` derives the screen's colours from the theme tokens (a MutationObserver on `data-theme` refreshes them) with a dark and a light ANSI palette; `terminal-store.ts` holds the list, the settings, the saved config and the trust; `terminal-panel.ts`, `terminal-dialog.ts`, `terminal-menu.ts`, `terminal-settings.ts` draw the panel (a flex row between the layout and the status bar), the tab menu, the properties window and the Settings section. Keys typed in the panel are ignored by the program's global shortcuts (`#terminalPanel` is skipped in `global-bindings.ts`), and the native context menu guard lets the panel have its own menus.
- **Dragging** (`terminal-drag.ts`; pure rules `placeBeside`, `swapLeaves`, `moveId` in `terminal-model.ts`; `dropTerminal` and `moveTerminalTab` in the store): pointer-based like the editor groups, the zone under the pointer comes from their `dropZone` and is drawn with their `.group-drop-overlay`. Terminal commands are `async` (off the main thread), the list of terminals is locked only for a lookup, every session has its own lock, and a command that cannot get it within 3 seconds answers "the terminal is not responding" instead of piling up; `terminal_spawn` ends and replaces a leftover session of the same id.
- **Terminal + preview mode** (`terminal-side-mode.ts`): the terminal panel is moved into the layout next to the preview (`body.side-terminal-mode` hides the editor pane and its divider), both share one `--side-terminal-grow` variable set on the layout; a divider of its own is dragged or moved with the arrow keys (20-80%, remembered). The Split button splits downward in this mode (up to `MAX_PANES` terminals stacked). Hiding the panel leaves the mode.
- **Fence language suggestions** (`fence-completion.ts`, pure rules in `fence-model.ts`): offered after a fence in Markdown; `fenceAt` tells an opening fence from a closing one and whether the block already has its closing line (the next fence line decides: a bare one closes, one with a language opens another block).
- **Running a code block** (`terminal-run.ts`; pure matching in `terminal-model.ts`: `languageFamily`, `shellFamily`, `pickShellFor`, `commandText`): the "Run" button that `code-blocks.ts` adds to bash/PowerShell/cmd blocks loads `terminal-run` on click, picks the most recently focused terminal whose shell fits the script (else creates one with a fitting shell, else the default shell with a note), waits for its shell to run, types the cleaned text with Enter and focuses it. The click is the user's consent; nothing runs from a note by itself.
- **Split and full screen**: what is on screen is a layout tree (`Layout` in `terminal-model.ts`: a pane, or a split of parts side by side or one above the other, nested; `splitLayout`, `removeLeaf`, `replaceLeaf`, `normalizeLayout` and `parseLayout` are pure and tested). Splitting splits the focused pane in the chosen direction (the same direction joins its split, another one makes a split of its own), at most 4 panes; the layout is kept in `localStorage` and `terminalState.panes` is its terminals in reading order. `terminal-panes.ts` draws the tree (a bar per pane, splitters between the parts) and rebuilds the DOM only when the layout changes, so typing is never interrupted; screens are moved into their panes with `TerminalSession.mount`, and each pane's ResizeObserver refits its xterm and tells its pty the new size. Focusing a pane makes its terminal the active one; opening a terminal that is not on screen replaces the one in focus. Full screen is a class on the panel (`position: fixed; inset: 0`), not remembered between runs.
- **Project config** (`src/project/project-config.ts`): `typenova.config.json` in the root of each open project folder (a visible name on purpose: a hidden folder would not be reached by the file system grant of every system). It holds `terminals` (id, name, shell id, folder relative to the project, startup command) and `activeTerminal`; unknown parts are kept, a file that is not a JSON object is never overwritten, writes are queued and skip an unchanged text. Shells start lazily: a restored terminal's shell starts when it is first shown.
- **Trust**: a project file can come from anywhere (a cloned repository), so it can name only a shell *id* (resolved against the computer's own list and the user's own shells; unknown ids fall back to the default), a folder that stays inside the project (`cleanRelativeFolder` drops `..` and absolute paths) and a startup command. A startup command runs only after the user approved that exact command (`commandHash`, kept in `localStorage`, not in the project); commands typed in the terminal window are trusted when written there.

## 8. Session, windows and recovery

- Open file-backed tabs are persisted as paths only (`typenova.openSession.v1`, `localStorage`), gated by `startupSessionReady`; paths that cannot be read are skipped and reported, and a blank `Untitled.md` is the fallback. Startup order: restore tabs, initialize editor and preview, then offer recovery of unsaved work (the recovery record must not be cleared before that).
- Editor and preview scroll positions are remembered per document, also across restarts. Tabs can be dragged out into a new window or into another TypeNova window (Rust window commands and a drag ghost); the format of a document travels with the tab. The app quits when the last editor window closes.
- Hidden sections are stored in `<file>.md.config.json` next to the document and excluded from editor, preview, print and export.

- **Bookmarks** (`src/editor/bookmarks*.ts`, `bookmark-field.ts`, `bookmark-dialogs.ts`, `src/app/bookmark-menu.ts`, `bookmark-sidebar.ts`): the list lives in `localStorage` (`typenova.bookmarks.v1`) and is the source of truth; each entry has a path, line, column, the line's text (excerpt), an optional name and note, and a never-reused number for the generated name. `bookmarks-model.ts` is pure and tested. In the editor a `StateField` holds one point marker per bookmark of the open file; markers map through every edit (`startSide`/`endSide` 1, so text typed at a marker does not drop it or leave it behind), and after each edit the stored line, column and excerpt are synced from them. When a tab becomes active the markers are rebuilt from the list, and a bookmark whose line no longer has its text is searched for within 200 lines. Only saved files can carry bookmarks (unsaved documents have no path). Code that replaces the editor state must call `refreshBookmarkMarkers()` after `view.setState`. For a Markdown document the bookmarks are also written to the document's config file (see below), without a folder path, so they survive a moved folder. The program's list stays the cache: a document's file is read once, the first time the document is shown, and replaces that document's entries; afterwards it is only written (a queue writes only files whose text changed). The setting `typenova.bookmarkFiles` (on by default, shared with highlights) turns reading and writing off; the tree rename moves the config file along with its document.
- **Show white space** (`src/editor/whitespace-extension.ts`, `src/app/whitespace-toggle.ts`): a CodeMirror `Compartment` holds `highlightWhitespace()` (spaces, tabs) plus a view plugin that adds an inline `¶` widget at the end of each visible line (a widget, not CSS, so empty lines keep their height). The toolbar button `#toggleWhitespace` is a toggle (`aria-pressed`, `selected`), stored in `typenova.showWhitespace`, reconfigures every open tab and the active view, and is a movable toolbar button (its label in the overflow menu comes from `data-overflow-text`).
- **Spell checking** (`src/spelling/`, `src-tauri/src/spell.rs`, `src-tauri/dictionaries/`): the webview has no spell checker that can be given a language or asked for suggestions (WebView2 follows the system language, and the native context menu is off), so the program has its own. The backend embeds the Hunspell dictionaries `pl` and `en` and reads each on first use with the `spellbook` crate (the Polish one in about 140 ms; a JavaScript Hunspell took 11 s and 470 MB for it); the commands `spell_check` (a word is right if it is right in any asked language; a hyphenated word if all its parts are) and `spell_suggest` run on a blocking thread. `spell-model.ts` is pure and tested: it blanks out what is not prose (addresses, code, markup, formulas, paths), finds words, skips acronyms and camelCase, and keeps the language setting and the personal word list. `spellcheck.ts` is a CodeMirror `ViewPlugin` that collects the words of the document (the Markdown syntax tree gives the code and URL ranges to skip; a document over 300,000 characters is checked around the viewport only), asks the backend only for words it has no answer for (a cache keyed by the word as written), and sets `cm-misspelled` marks through a `StateField` (mapped through edits). Words the user added or ignored are filtered in the front end, so changing them needs no new request. The context menu gets a `#spellMenuSection` filled for the word under the pointer; `Ctrl+.` opens the same menu at the caret.
- **Document config file** (`src/documents/doc-config-model.ts`, `doc-config.ts`): `notes.md.config.json` is the one file next to a document. It holds `hiddenSections` (and `focusedSection`), `bookmarks` and `highlights`; unknown parts are kept. `updateDocConfig` reads the file, lets one part change and writes it back (or removes it when nothing is left), through a single queue, so the three writers never overwrite each other; a file that is not a JSON object is never overwritten (`DocConfigUnreadable`). Bookmarks from the former `notes.md.bookmarks.json` are read as a fallback and moved on the first write.
- **Highlights** (`src/editor/highlights*.ts`, `highlight-field.ts`, `highlight-browser.ts`, `highlight-dialogs.ts`, `src/app/highlight-menu.ts`, `highlight-sidebar.ts`, `src/preview/preview-highlights.ts`): a highlight is a character range of a document with its text, a note, a group name and one of five colours. `highlights-model.ts` is pure and tested (overlap rules, relocation by text, grouping, Markdown export, `plainText` for the preview). The list lives in `localStorage` (`typenova.highlights.v1`) and in the config file; a `StateField` holds one mark decoration per highlight of the open file (`tn-hl-<colour>` classes, mapped through edits and synced back to the store; a highlight whose text was deleted is removed). In the preview, `applyBlockHighlights` runs on every rendered block: it takes the part of the highlight that lies in the block's lines, turns its source into the text a reader sees (`plainText`), finds it in the block's text nodes (white space collapsed) and wraps it in `mark.tn-highlight`; `refreshPreviewHighlights` redraws the blocks on screen. The left panel view and the project-row button work like the bookmarks ones.
- **Editor groups** (`src/documents/group-model.ts` (pure, tested), `groups-state.ts`, `groups-dom.ts`, `groups.ts`, `src/editor/editor-view.ts`, `src/styles/editor-split.css`): the editor area is a tree of splits whose leaves are groups (`Layout` in the model, at most `MAX_GROUPS`); each group has its own strip, its own `EditorView` and its own tab ids, and a tab belongs to exactly one group, so every tab has exactly one live editor state. `view` from `editor-view.ts` is always the editor of the group in use (reassigned by `setActiveView` when a group gets the focus), so the 40-odd modules that import `view` work on the active group without knowing about the split, and `documentState` keeps mirroring the active tab. `groups.ts` holds the operations: `focusGroup` saves the state of the group being left on its tab (`saveActiveTab`) and shows the other group's tab without reloading it (`showTab(tab, false)`), while `switchToTab` loads a tab into the group in use (or focuses the group that holds it); `moveTabToGroup`, `splitWithTab` (a new group beside a group), `mergeGroups` and `detachTabsFromGroups` (called before tabs close: a group shows its neighbouring tab, an empty group disappears, the last one stays). `reconcileGroups` runs from `renderTabs` so flows that still push to `documentState.tabs` (opening files, recovery) land in the group in use, and `orderTabs` keeps that list in the order the user sees. `groups-dom.ts` draws the layout (nested `.editor-split` elements with draggable, keyboard-operable dividers; the editors keep their documents and their scroll positions are put back), gives every group beyond the first its own strip (the first uses the strip of the page, which stays above the formatting toolbar while there is one group), moves the minimap into the only group (`setMinimapHost`) and finds where a dragged tab would land (`dropTargetAt`, with `dropZone` from the model). Anything that concerns the whole editor goes through `dispatchToAllViews` (theme, wrapping, line numbers, white space), and DOM listeners that belong to an editor are registered with `registerViewSetup`, which also runs them for editors created later; handlers of the scroll and the image preview act only for the editor in use. The layout and the files of each group are stored in `typenova.groups.v1` and restored after the open session; only saved files are restored, and a group left without a file disappears.
- **AI assistant** (`src/ai/`, `src/app/ai-provider-fields.ts`, `src/app/ai-settings-bindings.ts`, `src-tauri/src/ai.rs` with `src-tauri/src/ai/`, `src-tauri/src/secrets.rs`): several providers, exactly one on. The providers are one list, `AI_PROVIDERS` in `providers.ts` (pure, tested): each entry says which protocol it speaks (`adapter`), whether it needs a key, an address, and whether its models are fixed or asked for. Everything else is worked out from it: the cards and the fields of the options window (`ai-provider-fields.ts` draws one group per provider, so there is no hand-written HTML per provider), the model chooser (`model-select.ts`), what a provider still lacks (`readiness`) and the target of a request (`backendTarget` in `ai-settings.ts`). Adding a provider that speaks a known protocol is an entry in the list and a key name in `secrets.rs`; a new protocol also needs an adapter. The requests are made by the backend, not the webview: `ai_chat` resolves the target, reads the key and calls the adapter of the protocol (`anthropic.rs`, `openai.rs` for OpenAI and every compatible service, `gemini.rs`, `ollama.rs`), which builds the HTTP request with `ureq`, reads the stream and sends the text to the interface through a Tauri `Channel`; `ai_cancel` stops a request; `ai_list_models` asks the service for its models, which is also what "Check the connection" does. Claude and Gemini are always contacted at their own address; only OpenAI-compatible services and Ollama take one from the user. Failures come back as `{ kind, status, message }` (`classify` understands the error shapes of Claude, OpenAI and Google) and `describeAiError` / `connectionStatus` turn them into messages. Each API key lives in `secrets.rs` under `<provider>-api-key` from a fixed list of names: sealed with AES-256-GCM (the name is authenticated data) with a key derived by HKDF-SHA256 from a random per-installation secret file (private to the user on Unix) and the machine identifier, so it works the same on every system and the encrypted file is useless alone. The interface can only ask whether a key exists and for its last four characters (`secret_info`); the backend reads it itself when it makes a request, so the webview never holds it and the Content Security Policy needs no network exception. It protects against reading the settings or one copied file, not against a program running as the same user on the same machine. `ai-model.ts` is pure and tested (prompts, clipped context, the `<replacement>` format, code-block splitting, line diff). `chat-panel.ts` is the right-hand pane: it takes width from the three-pane layout through `layoutState.reservedRight`, its splitter is drawn like the other splitters, and `chat-context.ts` lists what is sent (document path, selection with its section from the outline). The top-bar button and the pane title are provider-neutral ("AI Chat"). `edit-dialog.ts` streams a proposal for the selection, shows it with `lineDiff` and replaces the selection only on Apply (after checking that the text is unchanged). Refusals and a cut-off answer are reported; the server-side refusal fallback is not enabled.

## 9. UI, themes and accessibility

- Themes: light, midnight, newsprint, retro and contrast, defined as tokens in `foundation.css`; use `--ui-*` tokens, not fixed colours. Honour `prefers-reduced-motion`.
- Every stateful button or segmented switch needs a persistent selected state tied to `aria-pressed`/`aria-checked`/`aria-selected`; hover alone is not enough. Buttons use SVG icons only. Tooltips and accessible names are localized explicitly in Polish and English through `langText()` or `data-pl`/`data-en`. The full checklist is in `.claude/skills/typenova-ui-css/SKILL.md`.
